# Yuki-RepoGuide

> 让看不懂 GitHub 的人，也能真正逛懂 GitHub。

## 1. 项目定位

**Yuki-RepoGuide** 是一个面向开发者，尤其是初学者的 GitHub 项目导览工具。

它不只是“总结 README”，而是把一个陌生 GitHub 仓库重新整理成一份**容易理解、容易行动、适合学习**的项目导览。

Yuki-RepoGuide 想解决的问题是：

- 找到了一个看起来很厉害的 GitHub 项目，却不知道它到底是做什么的。
- README 里充满陌生技术名词，只能硬啃。
- 技术栈看到了，却不知道这些技术在项目里分别负责什么。
- Releases 页面看不懂，不知道应该下载哪个版本或安装包。
- 不知道项目是否适合当前学习阶段。
- 想模仿一个大项目，却不知道应该从哪一小块开始。

---

## 2. 核心理念

Yuki-RepoGuide 不应该只是一个“AI GitHub 总结器”。

更准确的定位是：

> **把 GitHub 仓库从「README + 源码」翻译成开发者可以快速理解并采取下一步行动的项目导览。**

项目应尽量遵循以下原则：

### 2.1 先提供可靠事实，再做解释

仓库名称、描述、语言、Release、更新时间、README 等客观信息，应优先来自 GitHub 本身。

AI 更适合负责：

- 用人话解释项目。
- 解释技术栈各自的作用。
- 总结 Quick Start。
- 判断学习难度。
- 结合用户情况给出学习建议。
- 将大型项目拆成更适合练习的 Mini 版本。

### 2.2 技术从需求中长出来

不为了简历或“技术栈丰富”硬塞 Redis、MQ、Agent 等技术。

只有当真实需求出现时再引入，例如：

- 分析结果重复请求很多 → 缓存。
- GitHub API 有额度限制 → 限流 / 缓存。
- 大仓库分析耗时很长 → 异步任务。
- 用户想收藏项目 → 登录 / 数据库。
- 宿主 AI 需要调用 RepoGuide → MCP。
- 需要固定的项目分析流程 → Skill。

### 2.3 先做小闭环，再逐步扩展

第一版不追求“自动理解整个 GitHub”。

先把最核心、最常见的体验做好，再由真实使用反馈决定下一步。

---

## 3. 理想项目导览页

用户输入一个公开 GitHub 仓库链接后，Yuki-RepoGuide 应尽量提供以下内容。

### 3.1 一句话介绍

让用户在几秒内知道：

> **这个项目到底是干什么的？**

同时展示：

- 项目名称
- Logo / 项目图片（如果存在）
- GitHub 简介
- Stars 等基础信息

---

### 3.2 技术栈导览

不只展示：

```text
TypeScript 83%
Python 10%
...
```

还应该尽量解释：

- 主要语言是什么。
- 使用了哪些重要框架或技术。
- 这些技术在项目中分别承担什么角色。
- 哪些技术是核心，哪些只是辅助。

目标不是“列技术名词”，而是帮助初学者理解：

> **这个项目为什么需要这些技术？**

---

### 3.3 Quick Start

将 README 中的安装和运行步骤重新整理成更容易阅读的形式。

例如：

- 环境要求
- 安装步骤
- 启动命令
- 必要配置
- 常见注意事项

重点是减少用户在长 README 中来回寻找关键信息的成本。

---

### 3.4 Releases 导览

这是 Yuki-RepoGuide 一个很值得重点打磨的功能。

GitHub Releases 对初学者经常不够直观，例如：

```text
xxx-windows-x64-setup.exe
xxx-darwin-arm64.dmg
xxx-linux-x86_64.AppImage
...
```

Yuki-RepoGuide 应尽量重新组织为：

```text
Windows
→ 普通 64 位 Windows 电脑
→ 推荐下载 xxx-setup.exe

macOS
→ Apple Silicon
→ 推荐下载 xxx-arm64.dmg

Linux
→ ...
```

并辅助解释：

- Stable / Pre-release 的区别。
- 当前最新版本。
- 各安装包适合什么系统。
- 用户通常应该选择哪一个。

---

### 3.5 学习适配度

如果当前运行环境或宿主 AI 已经了解用户的学习情况，可以进一步回答：

- 这个项目当前是否适合完整学习。
- 哪些部分已经具备基础。
- 哪些知识暂时缺失。
- 哪些技术可以先忽略。
- 建议先从哪个模块切入。

例如：

> 完整复刻 AIRI 当前跨度较大，但可以先学习其中的文本角色聊天、简单记忆或某个独立模块。

---

### 3.6 Mini 版本建议

对于大型项目，Yuki-RepoGuide 不应该只给出：

> “项目很难。”

而应该进一步帮助用户回答：

> **如果想通过模仿这个项目来学习，最小应该做什么？**

例如：

```text
原项目：
AIRI

Mini 版本：
单角色
→ 文本聊天
→ 简单长期记忆
→ Web 页面

暂时不做：
Live2D
实时语音
游戏控制
复杂 Agent
```

这一能力可以成为 Yuki-RepoGuide 很有辨识度的功能之一。

## 4. 产品形态

Yuki-RepoGuide 可以设计成“一个核心，多种入口”。

### 4.1 Web

面向普通用户。

最基本流程：

```text
GitHub Repo URL
        ↓
Yuki-RepoGuide
        ↓
项目介绍
技术栈
Quick Start
Releases
        ↓
项目导览页
```

无需依赖任何 Agent，也能独立使用。

---

### 4.2 MCP

面向 Codex、Claude、OpenCode、DSH、ChatGPT 等支持工具调用的 AI / Agent。

Yuki-RepoGuide 负责提供可靠、结构化的仓库信息。

宿主 AI 可以进一步结合自己已有的用户上下文进行个性化解释。

例如：

```text
inspect_repo("moeru-ai/airi")
```

返回结构化信息：

```json
{
  "summary": "...",
  "languages": ["TypeScript"],
  "quickStart": {},
  "releases": [],
  "repoStructure": []
}
```

这样可以避免 Yuki-RepoGuide 自己维护完整的用户画像。

---

### 4.3 Skill

Skill 更适合负责“如何使用 RepoGuide 的能力”。

例如规定一个固定工作流：

1. 获取仓库事实。
2. 用一句话解释项目。
3. 解释核心技术栈。
4. 解释 Quick Start 和 Releases。
5. 结合当前用户水平判断学习适配度。
6. 如果跨度过大，拆出一个 Mini 复刻版本。
7. 明确哪些技术暂时无需学习。

可以理解为：

> **MCP 提供能力，Skill 规定工作方式。**

## 5. 第一版范围（V0）

V0 应尽量克制，只验证最核心的产品闭环。

### 输入

一个公开 GitHub 仓库 URL。

### 处理

从 GitHub 获取：

- 仓库基础信息
- README
- 主要语言
- Releases
- 必要的其他公开信息

### 输出

一张简单清晰的项目导览页，至少包含：

1. 一句话介绍
2. 基础项目信息
3. 技术栈
4. Quick Start
5. Releases 导览

### V0 暂时不做

- 自动读取完整代码库
- RAG
- 向量数据库
- 复杂 Agent
- 社区
- 排行榜
- 推荐算法
- 多人协作
- GitHub 登录
- 复杂用户画像
- 自动架构图
- 大规模源码语义分析

这些方向只是可能性，不代表必须全部实现。

### V1：AI 解释层

增加：

- README / Quick Start 简化

## 7. 项目与 AI 的关系

Yuki-RepoGuide 可以使用 AI，但不应该让 AI 负责一切。

推荐的基本边界：

```text
GitHub
   ↓
可靠的仓库事实
   ↓
Yuki-RepoGuide Core
   ↓
结构化信息
   ├── Web 展示
   ├── MCP
   └── AI / Skill 解释
```

原则：

> **GitHub 负责事实，Yuki-RepoGuide 负责整理，AI 负责理解和解释。**

这样可以减少模型幻觉，也让核心服务在没有 AI 时依然具有价值。

---

## 8. 当前最重要的产品价值

Yuki-RepoGuide 最想解决的不是：

> “帮用户快速读完 README。”

而是：

> **帮用户快速知道这个项目是什么、怎么开始、当前能不能学，以及下一步应该做什么。**

最终希望达到的体验是：

```text
以前：
打开 GitHub
→ 硬啃 README
→ 看见一堆陌生名词
→ Releases 不知道下哪个
→ 不知道值不值得学
→ 关闭页面

Yuki-RepoGuide：
粘贴仓库
→ 几分钟内看懂项目
→ 知道怎么运行
→ 知道怎么下载
→ 知道自己的学习切入点
→ 决定下一步行动
```

## 9. 当前阶段结论

项目名称暂定：

# **Yuki-RepoGuide**

当前已经确定的是：

- 项目要解决的真实问题。
- 基本用户体验。
- Web / MCP / Skill 多入口思路。
- V0 的核心闭环。

- 缓存方案
- 前端技术栈
- 部署方式
- 是否需要账户体系

这些内容留到后续技术设计阶段进一步讨论。
